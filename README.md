# AWS Cloud-Based Application Usage & Transaction Analytics Pipeline

An end-to-end cloud data analytics portfolio project that simulates how a Data Analyst
works with data generated by a web/mobile application — from raw ingestion in the cloud
through cleaning, validation, modeling, SQL analysis, and a business-facing dashboard.

Designed to demonstrate skills required for roles like **Associate Data Analyst –
Application Development / Cloud Development**.

---

## 1. Business Scenario

A company runs a web/mobile application. The app produces five kinds of data:

| Source | Description |
|---|---|
| **Users** | Who the customers are (registration date, region, device, segment) |
| **Application Events** | Clickstream: logins, page views, searches, cart adds, checkouts, payments |
| **Sessions** | Derived from events — groups of activity bounded by a `session_id` |
| **Transactions** | Completed/failed purchases, amount, payment method |
| **Application Errors** | Errors thrown by the app, tagged to device/version |

**Business questions this project answers:**

1. How do users interact with the application?
2. Which features/events are used most frequently?
3. How many daily/weekly/monthly active users does the app have (DAU/WAU/MAU)?
4. Where do users drop off in the funnel (view → cart → checkout → payment)?
5. Which devices/platforms/app versions generate the most errors?
6. How does engagement (session frequency, event volume) correlate with transactions?
7. Which customer segments/regions generate the most revenue?
8. How does app performance (errors) affect business outcomes (conversion, revenue)?

See [`docs/business_questions.md`](docs/business_questions.md) for the full question bank
mapped to SQL queries and dashboard visuals.

## 3. Datasets Used

This project intentionally combines **real public datasets** rather than one single source,
because no single public dataset contains users + events + transactions + errors together.
This mirrors real companies, where a Data Analyst joins data from multiple systems
(product analytics tool, payments system, app monitoring tool).

| Dataset | Source | Used for | Real or Synthetic |
|---|---|---|---|
| **eCommerce Events History in Cosmetics Shop** | [Kaggle – mkechinov](https://www.kaggle.com/datasets/mkechinov/ecommerce-events-history-in-cosmetics-shop) | `application_events` (view/cart/remove/purchase), `user_sessions`, base for `users` | Real |
| **Brazilian E-Commerce Public Dataset by Olist** | [Kaggle – olistbr](https://www.kaggle.com/datasets/olistbr/brazilian-ecommerce) | `transactions` (`olist_order_payments_dataset.csv` + `olist_orders_dataset.csv`), customer region | Real |
| **Application Errors** | Generated in `src/transformations.py` from realistic error taxonomies, correlated with real device/version fields pulled from the events dataset | Synthetic (documented, see below) | Synthetic |

**Why errors are synthetic:** there is no well-known public dataset of raw application
error logs (device/app-version/error-type/timestamp) tied to real user IDs — this kind of
data is proprietary telemetry (Sentry/Crashlytics/CloudWatch logs) that companies don't
publish. Per the project brief, synthetic data is used *only* here, and it's built to be
statistically realistic: error rates vary by `device_type` and `application_version`,
correlate with session errors observed in the events data, and use real error taxonomies
(`NullPointerException`, `PaymentGatewayTimeout`, `SessionExpired`, `APIError5xx`,
`OutOfMemory`, `NetworkTimeout`, `AuthenticationFailure`). See
[`docs/data_dictionary.md`](docs/data_dictionary.md) for the exact generation logic.

**How the datasets are joined:** the cosmetics-shop `user_id` becomes the app's `user_id`.
A `users` dimension is derived from the first-seen event per user (registration date =
first `event_time`, device_type = most frequent device for that user, region assigned by
sampling Olist's real Brazilian state distribution, customer_segment computed from
lifetime spend once transactions are joined). Olist `customer_unique_id` values are mapped
1:1 onto the cosmetics-shop `user_id` pool so that a transaction can be joined to a user's
event history. This join strategy is documented in full in
[`docs/data_dictionary.md`](docs/data_dictionary.md) so it's transparent to anyone
reviewing the portfolio.

Download the two real datasets from Kaggle and drop the raw CSVs into `data/raw/`
(not committed to git — see `.gitignore` pattern in `aws_setup_guide.md`). Small
illustrative samples (schema-only, 10–20 rows) are provided in `data/sample/` so the
notebooks and scripts can be reviewed without downloading anything.

## 6. How to Run This Project

1. **Get the data** — download the two Kaggle datasets listed above into `data/raw/`.
2. **Explore & clean locally** — run `notebooks/01_data_exploration.ipynb`, then
   `notebooks/02_data_cleaning.ipynb` (calls `src/data_cleaning.py`,
   `src/data_validation.py`, `src/transformations.py`) to produce cleaned Parquet files
   in `data/processed/` (created locally, mirrors what would land in S3).
3. **Stand up AWS** — follow [`aws/aws_setup_guide.md`](aws/aws_setup_guide.md) to create
   the S3 buckets, IAM role, Glue crawler/catalog, and Athena workgroup, then upload the
   raw CSVs and processed Parquet to S3.
4. **Run SQL analysis in Athena** — execute the three scripts in `sql/`, in order:
   `data_quality_checks.sql` → `data_exploration.sql` → `business_analysis.sql`.
5. **Build the dashboard** — connect Power BI to Athena (via ODBC) or import the Athena
   query results as CSV, then follow [`powerbi/dashboard_documentation.md`](powerbi/dashboard_documentation.md)
   to reproduce the report pages and DAX measures.
6. **Write up findings** — fill in [`docs/insights.md`](docs/insights.md) with the actual
   numbers your run produces.
